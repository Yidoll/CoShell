# 主题和桌面升级设计

## Context

现有 App.vue 顶栏左侧三个入口依次为新建连接、新建命令、WebDAV 配置，右侧已有运行模式和刷新。main.ts 先挂载启动页。global.css 与 workbench.css 各有系统深色规则，TerminalView.vue 创建 xterm 时设置固定颜色。WorkbenchLayout.vue 已有本机界面偏好的存储先例。

桌面采用 Tauri 2。src-tauri/tauri.conf.json 和 Cargo 工作区当前版本均为 0.1.0，之前的 0.1.1 安装包使用打包配置覆盖版本。现有 .github/workflows/ci.yml 会构建三个目标并上传 CI 工件，正式发布还需要稳定地址、更新清单和签名。src-tauri/capabilities/default.json 目前只给主窗口基础权限。

## Goals / Non-Goals

在右上角设置中提供“外观”和“软件更新”。主题作用于本机当前桌面应用或浏览器来源。升级首版仅面向桌面稳定通道，由用户主动触发检查、下载、安装。自定义配色、主题云同步、定时更新、灰度发布和差分包不在本次范围。

## Decisions

### 主题启动与切换

在 main.ts 挂载启动页前读取独立的本机偏好键，保存值为 `system`、`light`、`dark`。设置显示保存的模式，页面根元素保存解析后的配色。跟随模式通过 `matchMedia('(prefers-color-scheme: dark)')` 监听变化。固定模式忽略系统事件。存储读写及媒体查询不可用时按主题规格降级。

把两个样式表中依赖系统深色的规则归并到根元素主题选择器。为背景、前景、边框、焦点、选区、错误和生产危险命令定义语义颜色，同步原生表单的 color-scheme 和页面 theme-color。运行中的 xterm 通过 options.theme 更新普通色和终端 ANSI 调色板，原实例继续承载输入、选区和滚动历史。设置对话框关闭后将焦点交回打开它的控件。

### 在线升级选型与调研结论

| 方案 | 对 CoShell 的影响 | 决定 |
| --- | --- | --- |
| Tauri 2 官方升级器 + GitHub Releases 静态清单 | 插件支持检查、分开下载与安装、签名校验和平台选择。仓库已有三个构建目标 | 首版采用 |
| Tauri 2 官方升级器 + 动态更新服务 | 可按设备或通道返回更新，但需要单独部署服务 | 有灰度发布需求时再评估 |
| 打开 Release 页面让用户手动安装 | 可用于旧版首次接入或平台安装失败后的恢复 | 保留为恢复路径 |

官方 v2 更新工件模式使用 `bundle.createUpdaterArtifacts: true`。Windows NSIS 的安装文件可直接作为升级包，macOS 使用 app.tar.gz。静态清单要求各平台条目含下载 URL 和签名文件的**内容**。Windows 调用安装步骤时应用会退出，所以“稍后”和活动工作检查都要发生在调用安装之前。[Tauri 官方升级器文档](https://v2.tauri.app/plugin/updater/)

### 客户端职责与状态

由 src-tauri 注册 tauri-plugin-updater，在 Rust 宿主封装检查、下载、取消、安装及进度订阅。通过 apps/desktop/src/lib/backend/api.ts 暴露统一契约，Tauri 适配层调用受限命令，HTTP 适配层返回 unsupported。前端只能传操作 ID，更新 URL、公钥、安装参数由宿主固定。发行说明以文本渲染。coshell-core 仅提供与平台无关的活动会话、文件操作和备份状态，不引入 Tauri 依赖。

桌面返回运行时版本、候选版本、发行说明及操作 ID。状态依次为待检查、检查中、已是最新或可更新、下载中、可安装、安装交接。进度有总大小时显示比例，未知时显示已下载字节。检查和下载使用有限超时，取消会终止对应请求并释放缓冲。仅接受当前操作的进度与结果，重复点击复用进行中的操作，失败后的手动重试产生新 ID。错误至少区分网络不可达、清单无效、平台无包、签名失败、工作未结束和安装失败。

下载完成后在本次进程内保留已验证的包，稍后可回到设置安装，退出应用后重新检查和下载。安装确认时由后端原子地检查活动工作并暂缓接收新的连接、传输或自动备份。已有工作则返回类型及数量，交回用户处理。安装交接失败时恢复正常操作。Windows 由安装程序接手，macOS 完成替换后请求重启。下次启动读取实际版本，避免把开始安装误报为完成。

### 正式发布与兼容

使用固定的 HTTPS 入口 `https://github.com/Yidoll/CoShell/releases/latest/download/latest.json`，资产 URL 指向具体正式标签。正式标签触发独立发布流程，先创建草稿 Release。发布前对齐标签、Cargo、Tauri、安装包内版本与清单的 SemVer 值，开发机打包覆盖值不可作为发布依据。正式分发要求安装端可匿名读取清单及资产，不把 GitHub 访问令牌置入客户端。

| 清单键 | 更新包 | 首次安装包 |
| --- | --- | --- |
| windows-x86_64 | NSIS 安装程序及对应 .sig | x64 安装程序 |
| darwin-x86_64 | Intel .app.tar.gz 及对应 .sig | Intel .dmg |
| darwin-aarch64 | Apple Silicon .app.tar.gz 及对应 .sig | Apple Silicon .dmg |

签名私钥与口令由正式发布环境注入，客户端仅内置公钥。各平台构建完成后由同一发布作业合成清单，对三个架构逐项验证版本、下载文件与签名，再将草稿作为稳定版发布。macOS 的 Developer ID 签名、公证及 Windows 的 Authenticode 与升级包签名分别验证，平台发行资质在首次正式发布前核实。保留上一稳定版的标签、资产及手动安装说明。旧版 0.1.1 没有检查入口，需要一次手动安装；后续以两个连续版本验证从应用内升级。

## Risks / Trade-offs

- 发布私钥丢失时，旧客户端无法信任新密钥。发布者需保存可恢复的私钥备份，无法用旧密钥签发过渡版本时通过官方手动安装包重新建立信任。
- Windows 开始安装后原进程无法继续显示错误。由系统安装程序展示交接后的结果，发行说明保留故障恢复入口。更新失败后的恢复以重新启动及数据可用性作为验收依据。
- 版本回退需考虑本机数据库兼容性。发布故障时先撤下有问题的更新，已升级设备通过更高版本的修复包恢复。本次不承诺自动降级或数据库回滚。
